### 0.2 六个动作

| 动作 | 状态 | 关键点 |
|---|---|---|
| 建单 create | 无 → 1 | 冻模板、冻钱、占枪、锁权益 |
| 启动 start | 1 → 2 | 条件更新抢状态；枪状态只是投影 |

## 1. 计价引擎：把一次充电切成段

### 一句话

把充电窗口按电价规则边界切成若干段，每段按自己的电价算钱，电量按段时长分摊，最后把各段金额相加。

### 核心代码

文件：src/main/java/com/chargeops/billing/BillingEngine.java:63

~~~java
public static BillingResult calculate(BillingRequest request) {
    List<LocalDateTime> cuts = buildCuts(request);
    List<Window> windows = toWindows(cuts, request.rules());
    List<BigDecimal> energyPerWindow = allocateEnergy(request.totalEnergyKwh(), windows);

    List<BillingSegment> segments = new ArrayList<>(windows.size());
    BigDecimal totalEnergyFee = ZERO_AMOUNT;
    BigDecimal totalServiceFee = ZERO_AMOUNT;
    BigDecimal totalAmount = ZERO_AMOUNT;

    for (int i = 0; i < windows.size(); i++) {
        Window window = windows.get(i);
        TariffRuleSnapshot rule = window.rule();
        BigDecimal energy = energyPerWindow.get(i);

        BigDecimal energyFee = energy.multiply(rule.energyPrice())
                .setScale(AMOUNT_SCALE, ROUNDING);
        BigDecimal serviceFee = energy.multiply(rule.servicePrice())
                .setScale(AMOUNT_SCALE, ROUNDING);
        BigDecimal amount = energyFee.add(serviceFee);

        segments.add(new BillingSegment(
                i + 1, rule.periodType(), window.start(), window.end(),
                window.seconds(), energy, rule.energyPrice(), rule.servicePrice(),
                energyFee, serviceFee, amount));

        totalEnergyFee = totalEnergyFee.add(energyFee);
        totalServiceFee = totalServiceFee.add(serviceFee);
        totalAmount = totalAmount.add(amount);
    }

    assertTiling(segments, request);
    assertEnergyConserved(segments, request);

    return new BillingResult(request.startTime(), request.endTime(), segments,
            request.totalEnergyKwh(), totalEnergyFee, totalServiceFee, totalAmount);
}
~~~

### 逐步拆

第 1 步：buildCuts，找切点。

~~~java
TreeSet<LocalDateTime> cuts = new TreeSet<>();
cuts.add(start);
cuts.add(end);

for (LocalDate day = start.toLocalDate(); !day.isAfter(end.toLocalDate()); day = day.plusDays(1)) {
    LocalDateTime dayStart = day.atStartOfDay();
    for (TariffRuleSnapshot rule : request.rules()) {
        addCutIfStrictlyInside(cuts, dayStart.plusMinutes(rule.startMinute()), start, end);
        addCutIfStrictlyInside(cuts, dayStart.plusMinutes(rule.endMinute()), start, end);
    }
}
~~~

- 起点和终点一定进集合。
- 每条规则在每一天的开始/结束分钟，换算成绝对时间。
- 只保留严格在 (start, end) 里的点。
- TreeSet 去重：12:00 会被前一条规则的 end 和后一条规则的 start 各加一次；不去重会出现零长度段。
- plusMinutes(1440) 就是次日零点，跨天不用特判。

第 2 步：toWindows，相邻切点配成段。

~~~java
for (int i = 0; i < cuts.size() - 1; i++) {
    LocalDateTime windowStart = cuts.get(i);
    LocalDateTime windowEnd = cuts.get(i + 1);
    int seconds = (int) Duration.between(windowStart, windowEnd).getSeconds();
    windows.add(new Window(windowStart, windowEnd, seconds,
            resolveRule(rules, windowStart)));
}
~~~

- 每个窗口用起点反查规则，不用中点。
- 起点只可能是 S 或规则边界，半开区间下必然命中唯一一条。
- 命中 0 条 = 缺口，命中 2 条 = 重叠，一次判断覆盖两种。

第 3 步：allocateEnergy，按段时长正比分摊电量。

~~~java
int[] cumulativeSeconds = new int[count];
int running = 0;
for (int i = 0; i < count; i++) {
    running += windows.get(i).seconds();
    cumulativeSeconds[i] = running;
}
int totalSeconds = running;

BigDecimal previous = ZERO_ENERGY;
for (int i = 0; i < count; i++) {
    BigDecimal cumulative = totalEnergy
            .multiply(BigDecimal.valueOf(cumulativeSeconds[i]))
            .divide(BigDecimal.valueOf(totalSeconds), ENERGY_SCALE, ROUNDING);
    allocation.add(cumulative.subtract(previous));
    previous = cumulative;
}
~~~

- 不是平均分，是按段时长占比分。
- alloc_i = round4(E × cum_i / S总) − round4(E × cum_{i−1} / S总)。
- 相邻两项相消，Σ分段电量精确等于总电量；最后一段不会吃负数余数。

第 4 步：逐段算钱。

~~~java
BigDecimal energyFee = energy.multiply(rule.energyPrice())
        .setScale(AMOUNT_SCALE, ROUNDING);
BigDecimal serviceFee = energy.multiply(rule.servicePrice())
        .setScale(AMOUNT_SCALE, ROUNDING);
BigDecimal amount = energyFee.add(serviceFee);
~~~

- 电费和服务费分别舍入到分，再相加。
- HALF_UP，不用银行家舍入：账单要能逐段核对。
- totalAmount 是各段 amount 相加，不是总电量 × 综合单价；所以分段之和等于总额是恒等式。

第 5 步：两个断言。

- assertTiling：分段首尾铺满窗口，中间不能断/重叠。
- assertEnergyConserved：分段电量之和等于输入总电量。
- 抛 IllegalStateException，不抛业务异常：走到这里是引擎 bug，应该是 500。

### 为什么这么做

- 纯函数：不读时钟、不读库、不持有 Mapper，能脱开 Spring 穷举单测。
- TreeSet 去重是需求：不去重会产生零长度段，撞 uk(order_id, start_time)。
- 按起点反查：同时检测缺口和重叠，不用另写一遍。
- 前缀和分摊：保证电量守恒，比平均分 + 最后一段吃余数稳。
- 金额由分段相加定义：系统里没有第二个独立算出的总额。

## 2. 建单：先冻模板，再抢枪，最后冻钱

### 一句话

建单是一个事务：校验三层设备 → 冻计价模板 → 估冻结额 → 插订单 → 占枪 → 锁权益 → 冻钱 → 写事件；任何一步失败全部回滚。

### 核心代码

文件：src/main/java/com/chargeops/service/impl/ChargingOrderServiceImpl.java:154

~~~java
@Transactional
public ChargingOrderVO create(OrderCreateDTO dto) {
    Long memberId = requireMemberId();
    memberService.assertActive(memberId);
    LocalDateTime now = LocalDateTime.now();

    PayMethod payMethod = resolvePayMethod(dto.getPayMethod());

    Connector connector = assertConnectorUsable(dto);
    assertConnectorFree(dto.getConnectorId());
    Vehicle vehicle = resolveVehicle(dto.getVehicleId(), memberId);

    Long templateId = stationTariffService.resolveTemplateIdAt(dto.getStationId(), now);
    BigDecimal estimate = estimateFreezeAmount(templateId, vehicle);

    ChargingOrder order = ChargingOrder.builder()
            .orderNo(bizNoGenerator.orderNo())
            .memberId(memberId)
            .vehicleId(vehicle == null ? null : vehicle.getId())
            .plateNo(vehicle == null ? null : vehicle.getPlateNo())
            .stationId(connector.getStationId())
            .chargerId(connector.getChargerId())
            .connectorId(connector.getId())
            .tariffTemplateId(templateId)
            .status(OrderStatus.CREATED.getCode())
            .frozenAmount(estimate)
            .discountAmount(ZERO)
            .refundAmount(ZERO)
            .payMethod(payMethod.getCode())
            .version(0)
            .build();
    orderMapper.insert(order);

    if (connectorMapper.occupy(connector.getId(), order.getId(), now) == 0) {
        throw new ConnectorOccupiedException(MessageConstant.CONNECTOR_OCCUPIED);
    }

    Long packageId = tryLockPackage(memberId, order.getId(), now);
    if (packageId != null && orderMapper.bindMemberPackage(order.getId(), packageId, now) > 0) {
        order.setMemberPackageId(packageId);
    }

    walletService.freeze(memberId, order.getId(), estimate);

    recordEvent(order.getId(), null, OrderStatus.CREATED, OrderEventType.CREATE,
            EventSource.USER, memberId,
            "枪 " + connector.getId() + "，计费模板 " + templateId + "，预估冻结 " + estimate,
            null, now);

    return ChargingOrderVO.from(order);
}
~~~

### 逐步拆

1. requireMemberId + assertActive：登录 + 账号可用。禁用账号不能建单；pay 刻意不查，避免冻结资金解不开。
2. assertConnectorUsable：站点、桩、枪三层都查，且校验归属；只查枪会出现站点 A、枪 B 的订单。
3. assertConnectorFree：提前拒绝，给用户可读文案；真正裁决在 occupy。
4. resolveVehicle：车辆可选；有车就查归属、查这辆车有没有在充。
5. resolveTemplateIdAt：冻结此刻这个站点用哪个模板；结算只认订单上的 templateId。
6. estimateFreezeAmount：容量 × 模板里最贵的一条单价，封顶 500；这是上界。
7. insert order：先插，拿到 orderId；status=1。
8. occupy：真正抢枪；影响 0 行 = 别人刚抢走，或枪已故障/维护；抛异常回滚。
9. tryLockPackage + bindMemberPackage：锁一份权益；锁不到不失败，按余额直充。
10. freeze：余额不足抛异常，订单、枪、权益锁一起回滚。
11. recordEvent：留事件。

### 关键 SQL：occupy

文件：src/main/resources/mapper/ConnectorMapper.xml:81

~~~xml
<update id="occupy">
    UPDATE connector
    SET status = 2,
        current_order_id = #{orderId},
        version = version + 1,
        update_time = #{updateTime}
    WHERE id = #{connectorId}
      AND status = 1
      AND current_order_id IS NULL
</update>
~~~

### 为什么这么做

- 先 insert 再 occupy：occupy 要写 orderId，必须先拿到订单 id。
- occupy 在 freeze 之前：钱冻上再回滚就是白冻一次；先抢枪，抢不到就不冻钱。
- occupy 和建单同事务：抢枪成功但冻钱失败时，枪口占用跟着回滚。
- 模板 id 冻在订单上：管理员中途改电价，在途订单仍按旧模板结算。
- 冻结额取最贵单价：不是精确值，是上界；宁可多冻，也别结算时余额不够。
- 一把枪同时只挂一单：真正靠 current_order_id IS NULL + status=1 的条件更新，不靠前面的 SELECT。

## 3. 启动：1 → 2，枪的状态只是投影

### 一句话

启动只做两件事：把订单从 1 条件更新到 2，把枪从已占用改成充电中；订单是真相，枪的状态只是投影。

### 核心代码

文件：ChargingOrderServiceImpl.java:428

~~~java
@Transactional
public void start(Long orderId, OrderStartDTO dto) {
    ChargingOrder order = loadOrder(orderId);
    LocalDateTime now = LocalDateTime.now();

    int rows = orderMapper.markStarted(orderId, now,
            dto.getStartMeterKwh(), dto.getStartSoc(), now);
    if (rows == 0) {
        throw statusConflict(order, OrderStatus.CREATED, OrderStatus.CHARGING);
    }

    if (connectorMapper.markCharging(order.getConnectorId(), orderId, now) == 0) {
        log.warn("订单启动充电但枪口占用记录不匹配：orderId={}, connectorId={}",
                orderId, order.getConnectorId());
    }

    recordEvent(orderId, OrderStatus.CREATED, OrderStatus.CHARGING,
            OrderEventType.START, EventSource.DEVICE, null,
            "起始电表读数 " + dto.getStartMeterKwh(), null, now);
}
~~~

### 逐步拆

1. loadOrder：读订单，拿 connectorId。
2. markStarted：WHERE id = ? AND status = 1，影响 1 行才算抢到。
3. 0 行：订单已经被别的请求启动/取消，抛冲突；这里不吞。
4. markCharging：WHERE id = ? AND current_order_id = ?，把枪改成 3。
5. 0 行只告警：订单才是真相；历史数据可能没有占用记录，不能因为枪状态不对就让订单永远充不了电。
6. recordEvent：写启动事件。

### 为什么这么做

- 条件更新而不是先查后改：两个并发启动请求都读到 1 会都成功；WHERE status = 1 让只有一个成功。
- 枪的状态只是投影：connector.status 是给人看的，订单状态才是事实。
- 不动钱：钱在建单时已经冻好了。

### 一个边界

start 现在用服务端 now，end 在设备带时间时用设备时间——两端时钟口径不一致。这是下一轮要统一的点，面试别把它说成“两端都用设备时间”。另外，start 方法上的注释还写着“设备上报的时刻优先”，但 markStarted 实际传的是 now；以代码为准，这也是要统一的点。

## 4. 结束：2 → 3，先保住“充电结束了”这个事实

### 一句话

结束充电先校验结束时间，再把结束事实落库；电表读数坏掉时订单转 9 异常挂账，但 end_time 和事件都要留下。

### 核心代码

文件：ChargingOrderServiceImpl.java:459

~~~java
@Transactional
public void end(Long orderId, OrderEndDTO dto) {
    ChargingOrder order = loadOrder(orderId);
    LocalDateTime now = LocalDateTime.now();

    boolean deviceReportedTime = dto.getEndTime() != null;
    LocalDateTime endTime = deviceReportedTime ? dto.getEndTime() : now;

    LocalDateTime billingStart = order.getStartTime() == null
            ? null : order.getStartTime().truncatedTo(ChronoUnit.SECONDS);
    LocalDateTime billingEnd = endTime.truncatedTo(ChronoUnit.SECONDS);

    // 手工补录且落在同一秒：按最短可计费窗口 1 秒处理
    if (!deviceReportedTime && billingStart != null && !billingEnd.isAfter(billingStart)) {
        billingEnd = billingStart.plusSeconds(1);
        endTime = billingEnd;
    }

    if (billingStart != null && !billingEnd.isAfter(billingStart)) {
        throw new ParamErrorException("结束时间必须晚于开始时间：开始 "
                + order.getStartTime() + "，结束 " + endTime
                + "（设备时钟可能偏慢，请校正后重报）");
    }

    String meterProblem = checkMeterReadings(order, dto);

    Integer durationSeconds = billingStart == null ? null
            : (int) Duration.between(billingStart, billingEnd).getSeconds();
    BigDecimal energy = meterProblem == null
            ? dto.getEndMeterKwh().subtract(order.getStartMeterKwh())
            : null;

    int rows = orderMapper.markEnded(orderId, endTime, durationSeconds,
            dto.getEndMeterKwh(), energy, dto.getEndSoc(), dto.getStopReason(), now);
    if (rows == 0) {
        throw statusConflict(order, OrderStatus.CHARGING, OrderStatus.SETTLING);
    }

    if (connectorMapper.markOccupied(order.getConnectorId(), orderId, now) == 0) {
        log.warn("订单结束充电但枪口占用记录不匹配：orderId={}, connectorId={}",
                orderId, order.getConnectorId());
    }

    recordEvent(orderId, OrderStatus.CHARGING, OrderStatus.SETTLING,
            OrderEventType.END, EventSource.DEVICE, null,
            "结束电表读数 " + dto.getEndMeterKwh() + "，电量 " + energy, null, now);

    if (meterProblem != null) {
        markAbnormal(orderId, meterProblem, now);
        return;
    }
}
~~~

### 逐步拆

1. deviceReportedTime：设备给了 endTime 就是设备说的；没给就是运维手工补录，用服务端时钟。
2. 截到整秒：和 BillingRequest 的归一化口径一致；不截的话 [T, T+0.5s) 会在入口放行、结算才炸。
3. 手工补录同秒兜底：充了不到一秒，设备又没有“重报更晚时间”这个动作；按 1 秒窗口处理，别把订单卡在 2。
4. 设备报的时间不兜底：设备报的时间是可核对证据，不能偷偷改成 start+1s；早了就拒绝，让设备校准后重报。
5. checkMeterReadings：起始读数缺失 / 结束读数倒退，返回原因；电量算不出就传 null。
6. markEnded：只写结束事实和读数/时长，不写金额；金额留给结算。
7. markOccupied：枪从 3 回到 2，仍归本单；结算期间不能让别人下单。
8. 事件 + 异常挂账：先写 END 事件，再根据 meterProblem 转 9；两个事实都不丢。

### 为什么这么做

- 事实先落库：充电结束是物理事实，不能因为结算失败就回滚掉。
- 金额后算：结算可能因为电价规则缺口失败，那时订单应该留在 3，可以重试。
- 异常挂账单独一步：end 已经成功了，markAbnormal 是后续动作；合成一步必然丢掉一个事实。
- 枪不释放：结算还要读这把枪的起始读数；直接放空闲会让别人插单。

## 5. 结算：3 → 4，先算钱，再 CAS，再写分段

### 一句话

结算先确认订单在 3，跑计价引擎，算权益抵扣，CAS 到 4，再批量写分段、释放枪、充电次数 +1。

### 核心代码

文件：ChargingOrderServiceImpl.java:545

~~~java
@Transactional
public void settle(Long orderId) {
    ChargingOrder order = loadOrder(orderId);
    LocalDateTime now = LocalDateTime.now();

    if (order.getStatus() == null || order.getStatus() != OrderStatus.SETTLING.getCode()) {
        throw statusConflict(order, OrderStatus.SETTLING, OrderStatus.PENDING_PAY);
    }

    BillingResult result = bill(order);

    BigDecimal discount = ZERO;
    if (order.getMemberPackageId() != null) {
        discount = applyPackage(order, result, now);
    }
    BigDecimal payAmount = result.totalAmount().subtract(discount);

    int rows = orderMapper.markSettled(orderId,
            result.totalEnergyFee(), result.totalServiceFee(), result.totalAmount(),
            discount, payAmount, now, now);
    if (rows == 0) {
        throw statusConflict(order, OrderStatus.SETTLING, OrderStatus.PENDING_PAY);
    }

    segmentMapper.batchInsert(toSegments(orderId, result, now));

    releaseConnector(orderId, now);
    connectorMapper.incrementChargeCount(order.getConnectorId());

    recordEvent(orderId, OrderStatus.SETTLING, OrderStatus.PENDING_PAY,
            OrderEventType.SETTLE, EventSource.SCHEDULED, null,
            "分段 " + result.segmentCount() + " 段，应付 " + result.totalAmount()
                    + "，优惠 " + discount + "，实付 " + payAmount, null, now);
}
~~~

### 逐步拆

1. 先判状态：不是 3 就直接报“当前是 X，要求 3”，不要等 bill() 抛“缺少电表读数”造成误导。
2. bill(order)：用订单上冻结的 templateId 取规则，跑 BillingEngine；规则有缺口就抛异常，事务回滚，订单留在 3 可重试。
3. applyPackage：四种权益按各自口径抵扣；抵扣不超过应付。
4. markSettled：WHERE id = ? AND status = 3，CAS 到 4，并一次性写死金额。
5. batchInsert：分段明细；撞 uk_segment_order_start 说明 CAS 漏了，整笔失败并告警。
6. releaseConnector：车充完、账结出来，枪释放；释放是幂等的。
7. incrementChargeCount：累计充电次数 +1，和 CAS 同事务；不能改成 REQUIRES_NEW/Async，否则会重复计数。
8. recordEvent：写结算事件。

### 关键 SQL

~~~xml
<update id="markSettled">
    UPDATE charging_order
    SET status = 4,
        energy_fee = #{energyFee},
        service_fee = #{serviceFee},
        total_amount = #{totalAmount},
        discount_amount = #{discountAmount},
        pay_amount = #{payAmount},
        settle_time = #{settleTime},
        update_time = #{updateTime}
    WHERE id = #{id}
      AND status = 3
</update>
~~~

### 为什么这么做

- 先 CAS 再写副作用：两个并发结算都会跑完计价引擎；先 CAS 让只有一个能写分段，另一个 0 行直接失败。
- 分段在 CAS 之后：撞唯一键说明 CAS 没挡住，整笔回滚，重试从 3 重新开始。
- 次数 +1 放在同一事务：提交当且仅当 CAS 提交，最终恰好加一次。
- 释放枪放在写分段之后：一次事务里只取一次枪行的 X 锁，且取得尽量晚，减少和管理员改枪的等待。

### 一个已知瑕疵

这里事件来源写的是 SCHEDULED，但 settle 实际只有管理端调用，没有定时任务调它；这是审计叙事的问题，不影响金额。面试如果被问“谁触发的”，要如实说管理端。

### 一句话

- 6 也能支付：用户充值回来点第二次，订单正停在 6；只认 4 会永远返回“状态不对”，钱还冻着。
- 5 不能重入：已支付只能退款，重收一次会让“一笔订单最多一条扣款流水”失效。

## 8. 钱包：冻结不是扣款，读余额必须在 UPDATE 之后

### 一句话

钱包把余额和冻结额分两列：冻结是把钱从 balance 挪到 frozen_amount，结算先解冻再扣款，每笔变动都写流水。

### 核心 SQL

        frozen_amount = frozen_amount + #{amount},

    SET frozen_amount = frozen_amount - #{amount},
        balance = balance + #{amount},
        version = version + 1,
        update_time = #{updateTime}
    WHERE member_id = #{memberId}
      AND frozen_amount &gt;= #{amount}
</update>

<update id="deduct">
    UPDATE wallet
    SET balance = balance - #{amount},
        version = version + 1,
        update_time = #{updateTime}
    WHERE member_id = #{memberId}
      AND balance &gt;= #{amount}
</update>
~~~

### 流水怎么记

文件：WalletServiceImpl.java:335

~~~java
private Wallet recordTxn(Long memberId, Long orderId, WalletTransactionType type,
                         BigDecimal amount, BigDecimal balanceDelta, BigDecimal frozenDelta,
                         String remark, LocalDateTime now) {
    Wallet after = walletMapper.getByMemberId(memberId);

    walletTransactionMapper.insert(WalletTransaction.builder()
            .transactionNo(bizNoGenerator.transactionNo())
            .memberId(memberId)
            .orderId(orderId)
            .type(type.getCode())
            .amount(amount)
            .balanceBefore(after.getBalance().subtract(balanceDelta))
            .balanceAfter(after.getBalance())
            .frozenBefore(after.getFrozenAmount().subtract(frozenDelta))
            .frozenAfter(after.getFrozenAmount())
            .remark(remark)
            .createTime(now)
            .build());

    return after;
}
~~~

### 逐步拆

1. freeze：balance 减、frozen 加；WHERE 里带 balance >= amount，余额不够影响 0 行。
2. releaseFrozen：frozen 减、balance 加；WHERE 里带 frozen >= amount，防止解冻得比冻的多。
3. deduct：balance 减；WHERE 里带 balance >= amount，余额不够影响 0 行。
4. 先解冻再扣款：先扣的话钱还在冻结里，可用余额可能不够，一笔本该成功的结算会被拒。
5. 读余额在 UPDATE 之后：调用方刚执行的 UPDATE 持有该行排他锁，SELECT 读到的一定是改后的值；先读后写会让两笔并发写出同一个 before。
6. 流水前后余额反推：balanceBefore = after.balance − balanceDelta；调用方必须保证 delta 和 UPDATE 的 SET 对应。

### 为什么这么做

- 冻结模型：下单时不知道充多久，直接扣会多扣；先冻结上界，结算多退少补。
- 余额判断在 WHERE 里：不是先查再判断，避免 TOCTOU；影响行数 0 就是余额不够。
- uk(order_id, type)：同一订单同一类型只能一条流水，重复支付/结算会被唯一索引挡住。
- 流水必须记 before/after：对账时能看出每一笔钱从哪来、到哪去。

2. 结算为什么必须先 releaseFrozen 再 deduct？

## 9. 枪口：一把枪同时只能有一个订单

### 一句话

抢枪靠 connector 的条件更新：status=1 且 current_order_id IS NULL；释放靠 current_order_id = orderId，天然幂等。

### 核心 SQL

文件：src/main/resources/mapper/ConnectorMapper.xml:81

~~~xml
<update id="occupy">
    UPDATE connector
    SET status = 2,
        current_order_id = #{orderId},
        version = version + 1,
        update_time = #{updateTime}
    WHERE id = #{connectorId}
      AND status = 1
      AND current_order_id IS NULL
</update>

<update id="release">
    UPDATE connector
    SET status = 1,
        current_order_id = NULL,
        version = version + 1,
        update_time = #{updateTime}
    WHERE current_order_id = #{orderId}
</update>
~~~

### 逐步拆

1. occupy 的 WHERE：id + status=1 + current_order_id IS NULL，三个条件一起才抢得到。
2. status=1 不能省：只判 current_order_id IS NULL 的话，故障/维护/离线的枪也能被下单。
3. release 的 WHERE：只有 current_order_id = orderId，没有状态条件；重复调、对从未占用的枪调，都是 0 行。
4. markCharging/markOccupied：谓词用 current_order_id = orderId，回答“这把枪现在是不是我这一单占着”。

### 为什么这么做

- 条件更新是唯一裁决点：前面的 assertConnectorFree 只负责给用户文案，真正并发裁决在 occupy。
- release 幂等：cancel / settle / markAbnormal 三处都可以直接调，不用先判断“还占着吗”。
- release 会覆盖管理员的故障位：这是已知取舍；用 CASE WHEN 保住故障位的话，current_order_id 会永久非空，枪既不能删也不能再下单，更糟。

### 10.1 缓存：先查缓存，没有再查库

文件：src/main/java/com/chargeops/redis/CacheClient.java:123

~~~java
public <R> R queryWithPassThrough(String keyPrefix, Long id, TypeReference<R> type,
                                  Function<Long, R> dbFallback, Long ttl, TimeUnit unit) {
    String key = keyPrefix + id;
    String json = stringRedisTemplate.opsForValue().get(key);

    if (StringUtils.hasText(json)) {
        return redisJsonUtil.toBean(json, type);
    }
    if (json != null) {
        return null;
    }

    R r = dbFallback.apply(id);
    if (r == null) {
        stringRedisTemplate.opsForValue().set(key, "", CACHE_NULL_TTL, TimeUnit.MINUTES);
        return null;
    }

    return r;
}
~~~

## 12. AutoFill：为什么不是 AOP，而是 MyBatis 插件

### 一句话

审计字段要在 SQL 执行前最后一刻填；MyBatis 的 Mapper 是 MapperProxy，Spring AOP 织不进去，所以改用 Executor.update 的插件。

### 核心代码

文件：src/main/java/com/chargeops/mybatis/AutoFillInterceptor.java:106

~~~java
@Override
public Object intercept(Invocation invocation) throws Throwable {
    Object[] args = invocation.getArgs();
    MappedStatement ms = (MappedStatement) args[0];
    Object parameter = args[1];

    Optional<OperationType> spec = specCache.computeIfAbsent(ms.getId(), this::resolve);

    if (spec.isPresent()) {
        Object entity = findEntity(parameter);
        if (entity != null) {
            apply(entity, spec.get());
        }
    }

    return invocation.proceed();
}
~~~

~~~java
private static void apply(Object entity, OperationType operationType) {
    LocalDateTime now = LocalDateTime.now();
    Long currentId = BaseContext.getCurrentId();

    if (operationType == OperationType.INSERT) {
        write(entity, AutoFillConstant.SET_CREATE_TIME, LocalDateTime.class, now);
        write(entity, AutoFillConstant.SET_CREATE_USER, Long.class, currentId);
    }
    write(entity, AutoFillConstant.SET_UPDATE_TIME, LocalDateTime.class, now);
    write(entity, AutoFillConstant.SET_UPDATE_USER, Long.class, currentId);
}
~~~

### 逐步拆

1. 拦截 Executor.update：MyBatis 的 insert/update/delete 都走这里，查询不拦。
2. 从 MappedStatement.id 解析 Mapper 接口和方法。
3. specCache 缓存“有没有 @AutoFill”，避免每次反射扫方法。
4. findEntity 从 ParamMap 的 arg0/param1 取第一个参数。
5. apply 按 INSERT/UPDATE 写审计字段；UPDATE 不覆盖 create_time/create_user。
6. setter 找不到直接抛异常，不静默跳过。

### 为什么这么做

- Mapper 不走 Spring AOP：MapperFactoryBean 返回的 MapperProxy 在 BeanPostProcessor 之后才创建，AOP 没机会织入；切点匹配、启动不报错，但一次都不触发。
- 插件在 MyBatis 执行链上：一定生效；填充发生在 SQL 执行前最后一刻，审计时间更准。
- 缓存“没有注解”也很重要：否则每个没标注解的 update 每次都要 getMethods()。
