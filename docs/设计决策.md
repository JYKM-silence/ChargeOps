## 一、业务复杂度从哪来

充电桩不是「换个名字的电商」——它的难点长在业务本身，不需要硬塞秒杀来制造压力：

| 维度 | 典型 CRUD 业务 | 充电桩运营 |
|---|---|---|
| 履约主体 | 人工操作 | 设备协议驱动，无人介入 |
| 计费方式 | 固定单价 × 数量 | **分时电价 × 充电量**，电费与服务费分离 |
| 订单时长 | 秒级 ~ 分钟级 | 数十分钟到数小时，**横跨多个计费时段** |
| 数据来源 | 用户点击 | **设备上报**（心跳 / 遥测，万级设备高频写入） |
| 一致性难点 | 库存扣减 | **余额冻结 + 三方对账** |

几个直接由此推出的设计约束：

- 一条充电订单可能跨过「低谷 → 平段 → 尖峰」三个时段，结算必须**按时间切分成多段分别计价**，且 `Σ分段金额` 必须严格等于订单总额（否则对不上账）
- **电价会调整，但在途订单和历史订单不能被影响** —— 所以计费模板 id 在下单时冻结进订单，结算阶段完全不碰模板表
- 一把充电枪同一时刻只能有一个订单，两个用户同时扫码必须有一个失败，且**不能靠 `synchronized`**
- 设备会**重复上报**同一条「充电结束」事件，重复上报绝不能重复扣款

## 二、数据库与迁移

### Flyway 接手表结构

迁移文件在 [src/main/resources/db/migration/](src/main/resources/db/migration/)：

| 文件 | 内容 |
|---|---|
| `V1__init_schema.sql` | 19 张表的完整 DDL（含每条索引的设计理由） |
| `V2__seed_data.sql` | 种子数据（13 条 `INSERT IGNORE`） |
| `V3__member_package_pay_amount.sql` | `member_package.pay_amount`（购买时的实付快照）+ `idx_mp_status_expire(status, expire_time)`。见下方「V3 为什么是两列加一个索引」 |

`sql/00_create_database.sql` 只管 `CREATE DATABASE`：**Flyway 连的是一个已经存在的库**，
它没有权限也没有语义去创建库。`sql/verify.sql` 是一段自检查询（每张表的列数），
**不是迁移** —— 它是给人看的，不该每次启动都打印一遍。

#### 三条必须记住的规则

1. **已应用的迁移永不修改，要改表结构就加 `V4__xxx.sql`。**
  `validate-on-migrate: true` 会把「有人改了已应用的迁移」变成一次**启动失败**
  （校验和不匹配）。这是正确的取舍：让两台机器的表结构悄悄分叉，
  比在一次启动时报错严重得多。

2. **`baseline-on-migrate: true` 是「相信」，不是「校验」。**
  引入迁移之前就已经存在的老库会被记成版本 1 然后**跳过 V1** ——
  Flyway 不会去核对那个库到底是不是 V1 的样子。所以老库上引入 Flyway 时，
  **必须手工做一次「库 vs V1」的比对**（`sql/verify.sql` 就是干这个的），
  否则买到的只是「从今往后」的保护，历史漂移原封不动。

  **本机这个库是从空库重建的**，V1 是真跑过的（不是 baseline 跳过的），所以
  19 张表 / 280 列 / 68 索引与「V1 + V3」严格一致，零漂移。
  注意 `sql/verify.sql` 里内联的期望值是 **279 / 67**，那是 **V1 单独**的数 ——
  差的一个列和一个索引正是 V3 加的 `pay_amount` 与 `idx_mp_status_expire`。
  在跑过 V3 的库上对不上是正常的，别去改库。

  历史表有两种长相，**看 `type` 那一列就能分辨这个库是怎么来的**：

  | 库的来源 | installed_rank 1 的 type | 含义 |
  |---|---|---|
  | 空库（本机现在这种） | `SQL` | V1 真执行过 |
  | 引入 Flyway 之前就存在的老库 | `BASELINE` | **V1 被跳过了**，没人核对过它 |

  带 BASELINE 的那个库，V2 执行时会打出若干条 `Duplicate entry ...` **WARN** ——
  那正是 `INSERT IGNORE` 在跳过已存在的种子行，WARN 不是 ERROR，迁移照常算成功。
  空库路径下一条 WARN 都不会有，因为种子是全新插入的。

3. **不要碰 `clean`。** `clean-disabled: true` 已经写进配置（Flyway 9 起也是默认值），
  显式写出来是为了让「它被关着」这件事可见 —— 在一个 baseline 过的开发库上
  误触发 `clean` 等于一把清空所有测试数据。也永远不要设 `clean-on-validation-error`。

#### 测试**不会**帮你跑迁移 —— 加完 `V3` 必须手工起一次应用 

`src/test/resources/application.properties` 里写着 `spring.flyway.enabled=false`，
**这是有意的**：测试库就是开发库，测试假定表已经在那儿了，让每个 `@SpringBootTest`
都去跑一遍迁移只会让 382 条测试变慢且互相打架。

于是有一个很贵的坑：**你写好了 `V4__xxx.sql`、`mvn test` 全绿，但那条迁移一行都没执行过。**
如果新代码用到了 `V3` 才加的列，全量测试会以
`Unknown column 'pay_amount' in 'field list'` 的形式炸掉 28 个用例 ——
**而报错指向的是 Service，不是迁移**。本轮就真的撞了一次。

**唯一正确的做法是启动一次应用**（`mvn spring-boot:run`，然后 Ctrl-C）：

```
Migrating schema `chargeops` to version "3 - member package pay amount"
Successfully applied 1 migration to schema `chargeops`, now at version v3
```

**千万不要用 mysql CLI 手工 `ALTER` 把列加上去。** Flyway 不知道你加过了，
下一次启动会**再执行一遍 V3** 并死在 `Duplicate column name` 上 ——
一个本来只是「忘了启动一次」的问题，变成了要手工去修 `flyway_schema_history` 的事故。

#### V3 为什么是「两列加一个索引」

```sql
ALTER TABLE member_package ADD COLUMN pay_amount DECIMAL(12,2) NULL COMMENT '购买时实付金额快照';
CREATE INDEX idx_mp_status_expire ON member_package (status, expire_time);
```

**`pay_amount`** 是退款路径的全部依据。它必须是一列**快照**，理由和
`charging_order.frozen_amount` 完全一样：退多少由**下单那一刻的事实**决定，
而不是由「现在这个 SKU 卖多少钱」决定 —— `charge_package.price` 随时可以被管理员改，
用它退款等于给早买的人退错钱。它**允许 NULL**：V3 之前就已经存在的行没有这个数，
而 `voidPackage` 遇到 NULL 会**拒绝退款**而不是按 0 退（见 `MemberPackageMapper.voidPackage`）。

**`idx_mp_status_expire`** 是给过期扫描任务用的。谓词是
`status = 1 AND locked_order_id IS NULL AND expire_time <= ?` —— `status` 是等值条件、
选择性最高，所以它必须是前导列；`expire_time` 只做残余过滤。
反过来建会被扫全表的过期权益，而这个表只增不减。

#### 为什么当初必须换掉手工脚本

老做法（`sql/chargeops.sql`，已删除）用 `CREATE TABLE IF NOT EXISTS`，
对**已存在的表是空操作**：表在，它就跳过，**一列都不会改**。
于是「改这个文件重跑就能改表结构」这句话**只对全新的库成立**。

这不是假设 —— P1c-3 就撞上了：DDL 文件里写的是
`charging_order.member_package_id`，而本机库里的列还是上一版的 `package_id`，表现是
**所有 `ChargingOrderMapperTest` / `ChargingOrderServiceImplTest` 一起报
`Unknown column 'member_package_id' in 'field list'`**（35 个错误）。

### 2. `connectionTimeZone` 必须写 `+08:00`，不能写 `Asia/Shanghai`

写成时区**名字**会导致启动直接失败：

```
java.sql.SQLException: Unknown or incorrect time zone: 'Asia/Shanghai'
```

这个报错极易被误解成「时区名拼错了」。真正原因是 MySQL 处理命名时区要查
`mysql.time_zone_name` 等几张表，而**那几张表默认是空的**：

```sql
SELECT COUNT(*) FROM mysql.time_zone_name;  -- 返回 0 就说明没导入
```

Windows 上尤其常见 —— `mysql_tzinfo_to_sql` 是 Unix-only 工具，Windows 安装包不带它。

用数字偏移 `+08:00` 绕开整件事（中国不实行夏令时，两者恒等），
再配 `forceConnectionTimeZoneToSession=true` 让数据库端的 `CURRENT_TIMESTAMP` 也走同一时区。

### 3. `datetime(3)` 的精度与四舍五入

`LocalDateTime.now()` 是纳秒精度，而审计列是 `datetime(3)`。落库时超出部分被
**四舍五入**（不是截断）：`.818918500` → `.819`。

写测试时踩到：拿内存里的对象和从库里读回的对象比，断言必然失败，
而失败信息长得像「字段被改掉了」，很容易误导到错误方向。
**正确做法是两边都从库里取。**

同一个坑对所有 `datetime(3)` 列都成立。


### 6. `DEFAULT` 只在字段**缺席**时生效 —— 两个把 null 变成 500 的机制

写 NOT NULL 列时，很容易相信「DDL 里有 `DEFAULT 0`，不传就是 0」。**在满列 INSERT 下这是假的。**

```sql
INSERT INTO t (a) VALUES (NULL);    -- ERROR 1048: Column 'a' cannot be null
INSERT INTO t (a) VALUES (DEFAULT);  -- 用到 DEFAULT
```

`DEFAULT` 的触发条件是「这一列没有出现在 INSERT 的列清单里」，**不是「值是 null」**。
本项目的 Mapper 全部是满列插入（列清单写死），所以**显式传 null 就是 errno 1048**。

配套的第二个机制在 Java 侧：**DTO 的字段初始值只挡「JSON 里没有这个键」**。
`{"openTime": null}` 是显式 null，Jackson 照常调 setter，**覆盖掉初始值**。

两条合起来是一条规则：**对 NOT NULL 列，「不传」和「传 null」必须在 Service 里被归一成同一件事**。
做法是把默认值写成 DTO 上的 `public static final` 常量
（`ChargePackageDTO.DEFAULT_STATION_ID` 等），字段初始值和 Service 兜底引用**同一个常量** ——
否则两处各写一遍 `0`，改了一处就会漂移，而漂移的表现是「同样的请求，一次成功一次 500」。

冒烟测试里这条被直接验证过：`stationId` 显式传 null 的请求，报出的错误和完全不传**一字不差**。


### 13. MySQL 的 `SET` 子句**从左到右求值**，后面的子句看得见前面刚改的值

这是 `member_package` 的结算语句写出来之后、被测试抓到的一个真实 bug，不是理论推演。

结算要在一句话里干三件事：扣量、释放锁、用尽则改状态。最初的写法把 `status` 放在最后：

```sql
-- ❌ 错的
UPDATE member_package
  SET remaining_kwh = remaining_kwh - #{usedKwh},
    locked_order_id = NULL,
    status = CASE WHEN remaining_kwh - #{usedKwh} <= 0 THEN 2 ELSE status END
 WHERE id = #{id} AND locked_order_id = #{orderId};
```

读起来很顺：「扣完之后，如果剩的 ≤ 0 就标记用尽」。**但 `CASE` 里的
`remaining_kwh` 读到的是上一行刚减过的值，于是「减 1 次」变成了「减 2 次」，
条件提前一步成立。**

这不是标准 SQL 的行为（标准里所有 `SET` 都读原值），是 MySQL 单表 `UPDATE` 的文档化语义。
后果在一张次卡上最明显：**剩 2 次、用掉 1 次之后，剩余确实是 1，`status` 却被置成了 2（已用尽）**——
用户还剩 1 次没用，第 10 次充电会被静默拒绝，而第 9 次就已经显示「已用尽」了。全程没有报错。

修法是把 `status` 挪到扣量**前面**，并且比较**原值**：

```sql
-- ✅ 对的
UPDATE member_package
  SET status = CASE WHEN remaining_kwh <= #{usedKwh} THEN 2 ELSE status END,
    remaining_kwh = remaining_kwh - #{usedKwh},
    locked_order_id = NULL
 WHERE id = #{id} AND locked_order_id = #{orderId};
```

「我有的 ≤ 你要扣的」⇔ 扣完 ≤ 0 ⇔ 用尽 —— 语义没变，只是不再依赖求值顺序之外的东西。
`settleDuration` / `settleTimes` 是同一个形状（次卡是 `remaining_times <= 1`）。

**真库上的对照实验**（`r` 是剩余量、`s` 是状态，初始 `(2, 1)`）：

| 写法 | 剩余 | 状态 | |
|---|---|---|---|
| 扣量在前，`CASE WHEN r - 1 <= 0` | 1 | **2 已用尽** | ❌ 还剩 1 次却标成用尽 |
| `CASE` 在前，`WHEN r <= 1` | 1 | 1 生效中 | ✅ |

**结论：这三个 `settle` 语句里的 `status` 不能为了「读起来更顺」挪到扣量后面。**
三个方法各自的 XML 注释和 javadoc 里都留了指回这里的标记，测试也钉住了这个行为
（`MemberPackageMapperTest.settleTimesShouldConsumeExactlyOne`）。

## 三、计费与订单

### 7. 计费模板的规则**不可变**，而这正是 `station_tariff` 存在的理由

`charging_order` 在下单那一刻把 `tariff_template_id` 冻结进去，所以电价调整不影响在途订单。

**但这条保证只在规则不可变时才成立。** 如果模板的规则还能改，已冻结的 id 就会指向
被改过的规则 —— 保证静默失效：订单金额照样算出来，只是和用户启动时看到的不一样。

所以 `TariffTemplateServiceImpl.saveRules` 有一道守卫：模板被任何 `station_tariff` 行引用时，
**拒绝修改规则**。要调价就新建一个模板版本，用 `effective_from` 绑定生效期。
守卫同时把新绑定拦在停用模板之外，但**不动已有绑定** —— 两条路径、两个判断。

边界值得记清楚：**冻结的是规则，不是模板头**。改名称/地区/说明/`status` 不经过守卫，
否则「改个说明」都会变成不可能。冒烟测试把这条边界两侧都走了一遍。


### 16. 挂账的来源是「**钱还冻着**」的订单，不是「**枪还占着**」的订单

`OrderStatus` 上原本只有一个 `holdingConnectorCodes()` = `{1,2,3}`（待启动/充电中/待结算）——
语义是「这笔订单还占着那把枪」，`listHoldingByConnector` 用它做设备重复上报的幂等判断，没问题。

`markAbnormal`（转 `9 异常挂账`）图省事复用了同一个集合，
但这两种「进行中」**不是一回事**，差在**钱**上：

| | 占着枪 | 占着钱 |
|---|---|---|
| 1 待启动 | ✅ | ✅ |
| 2 充电中 | ✅ | ✅ |
| 3 待结算 | ✅ | ✅ |
| **4 待支付** | ❌ | ✅ |
| **6 支付失败** | ❌ | ✅ |

充电结束之后枪就释放了（所以 4 / 6 不在「占着枪」里），
**但预估冻结的那笔钱还在冻结里**。而挂账恰恰就是冲着这类订单去的 ——
「钱冻着、账却结不掉」。用 `{1,2,3}` 的结果是
**`4 待支付` / `6 支付失败` 的订单永远进不了挂账，那笔冻结款没有任何代码路径能核销**。

修法是拆成两个方法：`holdingConnectorCodes()`（占枪）和 `holdingMoneyCodes()`（占钱，
含 4 和 6）。`markAbnormal` 用后者。**`holdsMoney()` 也据此把 `PAY_FAILED` 算了进去**。

### 17. `6 支付失败` 曾经是个死胡同；顺带记两条钱包的顺序后果

`OrderStatus` 的类注释里那张流转表一直写着 `6 支付失败 → 4 或 9`，
但**代码里没有任何一条边实现它**，而 `markPaid` 只接受 `status = 4`。后果：

- 用户充值回来点「重新支付」→ 状态不对，一直失败
- 那笔钱**永远冻在冻结里**（`holdsMoney()` 当时也不含 6，连挂账都进不去，见决策 16）

流转表承诺了「充值后重试」，代码没有兑现。修法是让 `markPaid` 接受 `status IN (4, 6)`，
并把文档改成 **`6 → 5` 直达**（不绕回 4）—— 因为钱从来没被扣过，
从 6 直接到已支付反而是最短且正确的路径。

顺带两条在写测试时才显形的钱包行为，都值得记住：

**① `walletService.settle` 是「先解冻、再扣款」。** 它的直接后果是：
**这一单能动用的钱不是 `balance` 一个数，而是 `balance + 本单的冻结额`。**

原因是 `wallet.balance` 的语义是「**已扣掉冻结**的可用余额」（见字段注释）——
冻结是把钱从 `balance` **挪进** `frozen_amount`，不是额外占用一笔。
解冻就是把钱挪回来。所以：

```
可动用的钱 = balance + 本单冻结额 = 冻结前的余额
```

拿 `payWithInsufficientBalanceShouldKeepMoneyFrozen` 的真实数字走一遍：

| 步骤 | balance | frozen | 说明 |
|---|---|---|---|
| 造数据 | 10.00 | 0.00 | `givenBalance(memberId, "10.00")` |
| 建单冻结 7.50 | **2.50** | **7.50** | 钱被**挪走**了，不是凭空冻结 |
| 支付时解冻 | 10.00 | 0.00 | 挪回来，能动用的就是这 10.00 |
| 扣 15.00 | — | — | `10.00 < 15.00` → **`BalanceNotEnoughException`** |

**别读成「10.00 + 7.50 = 17.50，够付」** —— 那 7.50 本来就是从这 10.00 里划出去的，
不是另一笔钱。我最初就是这么读的，于是按「余额 == 冻结额所以一定付不起」这个
**错的直觉**设计了一组前提不成立的数据，`payWithInsufficientBalanceShouldKeepMoneyFrozen`
因此**假通过了一次**（它其实走的是支付成功分支）。

会抛 `BalanceNotEnoughException` 的真正条件是：

```
balance + 本单冻结额 < payAmount
```

（测试里还顺带钉住了另一件事：**实付可以大于冻结额**。预估冻结是按容量 5.00 算的 7.50，
实际充了 10 度 = 15.00 —— 预估值只是「先冻这么多」，不是金额上限。）

 而且失败之后**整个事务回滚**：余额和冻结都回到原样（2.50 / 7.50），
订单退回 `4 待支付`。**钱没丢，充值后原样重试即可** —— 测试最后就是充到 100.00
再 `pay` 一次，断言 `100 + 7.50 − 15.00 = 92.50`。

**② `DEFAULT_BATTERY_KWH` 是兜底，不是中性值。** 建单时没传 `vehicleId` 就按 **60 kWh**
估冻结额，而不是按任何车辆的容量。测试里漏传车辆会让冻结额从 75.00 静默变成 90.00 ——
金额断言会在一个和被测逻辑毫无关系的地方失败。

## 四、权益

### 14. 折扣按「**被覆盖的**数量」算，扣减就必须按**同一个数** —— 否则 `remaining_*` 会变成负数

这条也是测试抓的，症状是 `remaining_kwh = -6.00`。

权益抵扣电量费时有两个数很容易混：

- `used` —— 这一单**总共**用了多少（比如 10 度）
- `covered` —— 这份权益**能覆盖**多少（比如包里只剩 4 度）

折扣当然按 `covered` 算：`discount = energyFee × (covered / used)`。
但最初的 `consumePackage` 扣的是 **`used`**。于是「剩 4 度的包被扣掉 10 度」，
`remaining_kwh` 成了 **−6**。

**它不报错、也不多收钱**（折扣是按 4 度给的，用户没吃亏），
但它把一个包变成了永久不可用：`listUsable` 的条件里有 `remaining_kwh > 0`，
负数永远不满足 —— 用户那 6 度差额**去哪了，界面上永远查不出来**。
这比多收钱更难排查，因为对账时金额是对的。

修法是把两个数收敛成一个：先算出 `covered`（含时长包**向下取整到整分钟**），
折扣和扣减**都**用它。`applyPackage` / `coveredAmountOf` 的注释里写了这条约束。

### 15. `tryLockPackage` 里的一个无条件 `break`，让只有非电量包的车主**永远选不中**

选可用权益时按 `PackageType.values()` 遍历（电量包 → 时长包 → 次卡 → 折扣包），
每种类型单独查一次。最初的写法是查到就 `break`。

问题在「查到」的定义是「这个类型的查询返回了结果」，不是「抢到了」——
一份**已被别的订单锁住**的电量包也会让查询返回结果，于是 `break` 直接跳出循环，
后面三种类型**一次都不试**。表现是：一个只持有时长包的车主，
名下有可用权益却永远走「无权益」路径（多付全额），而且**日志里什么都看不到**。

修法是遍历**所有**类型、每种都尝试锁定，抢不到就继续下一个候选。
正确的成本是「多几次查询」，换来的是「不会静默漏掉用户已经买过的权益」。


### 18. 套餐作废：**先 CAS，再打款** —— 反过来写就是一台重复退款的机器

`MemberPackageServiceImpl.voidPackage` 的顺序是固定的，而且**只有这一个顺序是对的**：

```java
int rows = memberPackageMapper.voidPackage(id, remark, now);  // ① 先把状态改成「已作废」
if (rows == 0) { throw ...; }                 // ② 0 行 = 这一份不归你
walletService.refundPackage(...);               // ③ 到这里才打钱
```

**为什么这个顺序是唯一安全的**：`PACKAGE_REFUND` 的 `order_id` 是 NULL，
而流水表的幂等靠的是 `uk_txn_order_type (order_id, type)` ——
**MySQL 的唯一索引不约束 NULL**，两行 `(NULL, 8)` 不冲突。
所以这条路径上**没有**数据库级的「一单只退一次」。

那唯一一次的保护就是 ① 那个 UPDATE 的谓词
（`WHERE id = ? AND status = 1 AND locked_order_id IS NULL`）。
它是一次 CAS：两个并发的作废请求里，**只有一个**能让 `rows = 1`。

**把 ① 和 ③ 对调会怎样？今天不会丢钱，但那是因为 `@Transactional` 恰好兜住了** ——
两个请求都先打款，其中一个的 CAS 返回 0 并抛异常，整个事务回滚，多出来的那笔钱被撤掉。
**所以这个顺序不是「今天靠它防重复退款」，而是「它是唯一让 CAS 成为裁决点的写法」。**
关键在于：一旦 `refundPackage` 里加了任何**不参与回滚**的副作用
（发 MQ、调支付网关、写外部账、发通知），对调就立刻变成一个真实的重复退款 ——
**「先裁决、后副作用」是钱路上不能靠事务兜底的性质**，而事务边界将来是会变的
（`REQUIRES_NEW`、异步、拆服务），CAS 和它保护的写之间隔着一行代码，是唯一稳的形状。
所以它有一条专门的测试
（`voidCasShouldLetExactlyOneWinnerThrough`），直接连调两次 Mapper 断言 `1` 和 `0`。

 **另一个方向的错误更隐蔽：把 `if (rows == 0)` 删掉。** 这时重复退款确实发生了，
但**什么都不会报错** —— 作废照常成功、权益照常变灰、车主看到的余额也确实变多了
（他会以为是别的钱）。这种「错得让所有人都满意」的缺陷只能靠测试发现，
所以 `voidTwiceShouldRefundOnlyOnce` 断言的是**流水条数**而不是余额。

顺带记一条**同一形状的守卫**，它在 `refundPackage` 里，而且**它是唯一的一道**：
`if (amount == null || amount.signum() <= 0) throw`。
调用方 `voidPackage` 那一侧也有一道 `if (payAmount.signum() > 0)`（赠送套餐不退款），
两道看起来重复，实际不是 —— **删掉调用方那一句，这里就是全部的保护**，
而症状是「零元退款流水」和「负金额从只进不出的钱包里被取走」两种，
两者都不报错。测试名 `refundPackageShouldRejectNonPositiveAmount` 钉的就是这件事：
`<= 0` 而不是 `== 0`，因为 `signum() == 0` 会放过负数。

## 五、数据建模

### 10. 「每车主至多一辆默认车」**不可能用唯一索引表达**

直觉是给 `vehicle(member_id, is_default)` 加个唯一索引就完事了。**那个索引会禁止
一个车主有两辆非默认车** —— 非默认行的 `is_default` 全是 0，第二辆立刻撞键。
MySQL 没有部分索引（`WHERE is_default = 1`）；业界绕法是让非默认行存 NULL
（唯一索引不约束 NULL），但 DDL 写的是 `is_default tinyint NOT NULL DEFAULT 0`，这条路也已经封了。

**所以 DDL 里那个「缺失的索引」不是疏漏，是这个约束在当前列定义下无法用索引表达。**
它落在两条条件更新上（`clearDefaultExcept` / `markDefault`），
关键细节是 `clearDefaultExcept` 的 `id <> #{id}` 是**正确性要求**：
新建第二辆默认车时是先 insert 再清旧的，那一刻新行在同一事务里已经可见且 `is_default` 已是 1 ——
没有这个排除条件，创建操作会把自己刚设的标记立刻清掉，而且**静默**（接口返回成功）。

不变量「有车的车主一定有且只有一辆默认车」由三条路径共同维护，
`VehicleServiceImplTest` 用内存假库把它逐条钉住（含「先清后置」的顺序、
删掉默认车后提升的是 `ORDER BY is_default DESC, id DESC` 的第一条 = **最新**那辆非默认车）。

### 11. 车牌转大写**不是为了唯一性**，`trim()` 才是

两条都已在真库上验证过（`VehicleMapperTest` 里是可执行的回归测试）：

- 库 / 列排序规则是 `utf8mb4_0900_ai_ci`，**大小写不敏感** ——
 `uk_vehicle_member_plate` **本来**就把 `粤BD12345` 和 `粤bd12345` 当同一个值。
 转大写的目的只是**展示统一**（列表页不出现两种写法）。**不要**把它改成 `_bin`/`_as_cs`：
 唯一约束和「客服按车牌反查车主」会同时静默改变行为。
- 但同一个排序规则是 **NO PAD** —— 它认为**尾随空格有意义**。
 于是 `'粤BD12345' = '粤BD12345 '` 返回 **0**，唯一索引**拦不住**带尾空格的重复车牌：
 实测能把同一块牌登记两次，产生两行看起来一模一样的记录。
 `VehicleServiceImpl.normalizePlateNo` 里那个 `trim()` 是目前唯一挡住它的事情。

`toUpperCase(Locale.ROOT)` 里的 `Locale.ROOT` 同理不是装饰：土耳其语区域下
`'i'.toUpperCase()` 是 `'İ'`，而那个 bug **只在 `tr_TR` 的服务器上出现**，本机永远复现不了。

### 12. 唯一键拆成 `uk(type, name)` 之后，**消费方必须知道自己要哪个 type**

DDL 把老的 `uk(name)` 改成 `uk_category_type_name (type, name)`，注释写着理由：
「『快充』既可能是套餐分类也可能是服务分类，全局唯一会误伤」。

**这个改动有一个不显然的后果：拆了 type 之后，`categoryId` 就不再足以确定一个分类了。**
指错 type 不会撞任何约束，只会**静默地**把套餐挂到一个「停车服务」分类下 ——
type 拆分于是只带来了歧义，没带来秩序。所以 `ChargePackageServiceImpl`
在校验「分类存在」之后还要校验「它是充电套餐分类」：

```
分类类型不匹配：充电套餐只能挂在「充电套餐分类」下，而分类「停车服务」是「增值服务分类」
```

**但刻意不校验 `category.status`。** 停用分类不该让已挂在上面的套餐无法改价
（否则改个价格要先去启用分类）。「下架分类」的语义是「不再出现在新建的下拉框里」，
不是「存量数据失效」—— 和 `TariffTemplateService` 里「停用模板不影响已有绑定」是同一个道理。

**写路径严格、读路径降级**，这条在项目里反复出现：校验只在 `create`/`update` 上，
而 `listEnabled` 之类的读路径遇到脏数据返回 `null` 标签而不是抛异常。

## 六、框架与配置

### 1. `@AutoFill` 为什么是 MyBatis 插件，不是 AOP 切面

公共字段自动填充的教科书写法是 `@Aspect` + `@Pointcut("@annotation(AutoFill)")`，
把注解开在 Mapper 方法上。

**这个写法在本项目里是静默失效的**：编译通过、启动成功、零报错，但审计字段永远是 `null`。

排查过程是一步步排除假设的：

```
aspectjweaver 在不在 classpath 上？       → 在
AnnotationAwareAspectJAutoProxyCreator 注册了吗？ → 注册了
切面 bean 存在吗？                → 存在
切点表达式匹配 StaffMapper.insert 吗？       → true
staffMapper 是 Spring AOP 代理吗？        → false  ← 问题在这
```

根因是**机制上不可能**：Mapper 接口对应的 bean 是 `MapperFactoryBean`（一个 `FactoryBean`），
Spring 容器先对**工厂对象本身**跑 `BeanPostProcessor`（切点永远匹配不上它），
之后才调 `getObject()` 拿到真正被调用的 `MapperProxy` ——
**这一步发生在所有 `BeanPostProcessor` 之后**，而 Spring AOP 的自动代理正是靠
`postProcessAfterInitialization` 织入的。代理没机会织进去。

所以调整 `proxy-target-class`、换 CGLIB、加 `@EnableAspectJAutoProxy` 全都没用，方向就不对。
改成 MyBatis 插件（拦截 `Executor.update`）后**机制上一定生效**。

> 副产品：这个 bug 是**写测试抓到的**。当时三条 P0 验收全绿 ——
> 这正是「接口能通」和「功能正确」是两件事的具体样子。

见 `mybatis/AutoFillInterceptor.java`。


### 4. `WebMvcConfigurer`，不是 `WebMvcConfigurationSupport`

继承 `WebMvcConfigurationSupport` 会**关掉 Spring Boot 的 MVC 自动配置** ——
静态资源（含 swagger-ui 的 webjar）、默认消息转换器全部失效。
表现为 swagger-ui 404、上传图片 404，而日志里没有直接线索。

排查这类问题时先访问 `/v3/api-docs`：**它是纯 JSON，不依赖任何前端静态资源**。
有 JSON → 文档数据是好的，问题在静态资源；没 JSON → springdoc 根本没生效。方向完全不同。

### 5. 依赖版本上的两个坑

- **Druid**：Boot 4 要用 `druid-spring-boot-4-starter`（artifactId 里有 `-4-`）。
 引错成普通的 `druid-spring-boot-3-starter` 会在启动时 `ClassNotFoundException: javax.servlet.Filter`
- **Boot 4 把 `spring-boot-starter-aop` 改名成了 `spring-boot-starter-aspectj`**。
 按老经验敲旧名字会报 `'dependencies.dependency.version' ... is missing` ——
 这个报错说的是「缺版本号」，但真实含义是「BOM 里没有这个坐标」


### 8. 两个只有跑起来才发现的 bug

单元测试和集成测试全绿，接口一调就炸 —— 这两条都是冒烟测试抓到的：

- **`charge_package.category_id` 是 NOT NULL 且无 DDL 默认值**，而 DTO 上忘了 `@NotNull`。
 不传分类 → 穿过校验 → 撞 insert → **HTTP 500 +「未知错误」**。
 这是「NOT NULL 无默认值的列必须在 DTO 层拦」这条规则的一个漏网之鱼
 （`charger.rated_power_kw` 拦了，它没拦）。
- **`assertEffectiveRange` 对 `effectiveTo` 直接调 `isAfter`**，而 `effectiveTo` 为 null
 （不填失效时刻 = 长期有效）是**最常见**的合法输入。于是「不填失效时刻」这个正常操作
 抛 NPE → 500 +「未知错误」。
 根因是判空写在了调用点而不是方法内 —— **把前置条件放进方法里，任何一个调用点都不可能再忘**。

两条的共同特征是**报错信息量为零**：调用方拿到「未知错误」，既不知道哪个字段，
也分不清是参数问题还是服务挂了。这类 bug 值得优先修，因为它们会掩盖后面所有的真问题。

### 9. 两个同名 Controller **能编译、能过 IDE、在启动那一刻炸**

P1c-1 加车主端时写了 `controller/user/AuthController`，而 `controller/admin/AuthController`
早就存在。结果是**整个应用起不来**：

```
ConflictingBeanDefinitionException: Annotation-specified bean name 'authController'
for bean class [com.chargeops.controller.user.AuthController] conflicts with
existing, non-compatible bean definition of same name and class
[com.chargeops.controller.admin.AuthController]
```

根因：Spring 的 `AnnotationBeanNameGenerator` 给 `@RestController` 的默认 bean 名是
**类的简单名首字母小写**，它**不看包名**。同名不同包在 Java 里完全合法，在 Spring 里不合法。

这个错误的性质比它本身更值得记：**它躲过了所有静态检查** ——
`mvn compile` 成功、IDE 不报错也不警告，只在容器启动那一刻出现。
抓住它的是 `@SpringBootTest` 那一组 Mapper 测试（它们要起容器），
报错还伪装成 39 个测试一起失败 + `ApplicationContext failure threshold exceeded`。

修法选了**改类名**（`MemberAuthController`），而不是给两个类写显式 bean 名：
后者把「不许重名」变成一条要记得的规则，下一个写 `AuthController` 的人还会再踩。
同一个决定在 `MemberAdminController` 上已经做过一次（它本来叫 `admin/MemberController`）。

**推论**：这个项目里所有 Controller 的类名都必须自带作用域。

## 七、AI 接入

### 19. `spring.ai.model.*` 的默认值是「自动装配」—— 关掉它必须显式写 `none`

这是接入 Spring AI 时最先撞上、也最容易误诊的一条。

云厂商的 starter（DeepSeek / OpenAI / Anthropic……）自动配置类上挂的是：

```java
@ConditionalOnProperty(name = "spring.ai.model.chat", havingValue = "deepseek", matchIfMissing = true)
```

而它的 bean 方法体里有 `Assert.hasText(resolvedApiKey, "DeepSeek API key must be set")`。

两件事合起来的后果是：**只要那个 starter 在 classpath 上、而 api-key 是空的，
应用就起不来，`mvn test` 也起不来**。报错是一句 `IllegalArgumentException: DeepSeek API key
must be set`，看起来像「api-key 配错了」，实际是「你什么都没配，但它默认要装配」。
实测漏关一个，382 个测试里 282 个报上下文加载失败。

这个项目最后选了 Ollama（本地跑，不需要密钥），上面那一串关闭配置因此都不需要 ——
**但判断方法没有变**：判断一个自动配置会不会生效，要看它的 `matchIfMissing`。
默认值不是「不装配」，而是「无条件装配」，这时候唯一的关闭方式就是显式给它一个不匹配的值。

配套的一条：`chargeops.ai-ops` 下没有 `enabled` 开关。开关必须放在框架那侧，
我们自己写的开关拦不住框架的自动配置 —— 那条 `@ConditionalOnProperty` 执行的时候，
我们的逻辑还一行都没跑。


### 20. Spring AI 2.0 里没有 `QuestionAnswerAdvisor`，RAG 是手写的

网上能搜到的 Spring AI RAG 示例几乎都是这样：

```java
.advisors(new QuestionAnswerAdvisor(vectorStore))
```

**这个类在 2.0 里不存在**（遍历本地仓库全部 spring-ai jar 确认过）。向量库 advisor 那一整块
被移出了核心，2.0 剩下的 advisor 只有记忆、日志、安全阀、工具调用、结构化输出这几类。

所以检索这一步是自己写的：`KnowledgeBaseService.search()` 用 `SearchRequest` 调
`VectorStore.similaritySearch`，把命中的片段拼进系统提示词，再发一次普通的
`chatClient.prompt().system(...).user(...)`。见 `AiOpsServiceImpl.systemPrompt`。

**这个「退化」其实是升级**：检索和生成拆成两个方法之后，`GET /knowledge/search`
可以只跑前半段、不调模型。排查「答得不对」时第一件要分辨的事就是
「知识库没内容」还是「模型没用好内容」，而这个问题在有 advisor 的写法里答不了。

已知短板记在这里：**追问里的指代检索不到东西**。「那第二点具体怎么做」整句向量化之后
召回为空，因为这句话里没有任何实词。要修得让检索用上一轮的轮次做查询改写，
那属于另一件事，本轮不做。


### 21. `.tools(bean)` 的 bean 一旦被代理，`@Tool` 会**静默地一个都不注册**

`ChatClient` 有两个入口能把对象上的 `@Tool` 方法变成可调用的工具：

| 入口 | 是否做 AOP 方法解析 |
|---|---|
| `MethodToolCallbackProvider` | **是**（用了 `AopUtils` / `getMostSpecificMethod`） |
| `ToolCallbacks.from(bean)` | **否** |

而 `.tools(Object...)` 走的是后者。遍历 `org.springframework.ai.tool` 下全部 67 个类确认过，
只有 `MethodToolCallbackProvider` 一个做了方法解析。

后果是：**给工具类加上任何生成代理的注解（`@Transactional`、`@Async`、`@Cacheable`……），
`@Tool` 就注解读不到了**。失败方式是最难查的那种 —— 不报错、日志里什么都没有，
模型只是回答「我没有查询实时数据的能力」。

所以 `OpsTools` 的类注释里明确写了不许加 `@Transactional`。这不算牺牲：
它唯一的写操作是一条 INSERT，本来也不需要事务。


### 22. `@ConditionalOnMissingBean` 按**方法返回类型**匹配 —— 一个词的差别，从「启动失败」到「自动退避」

`PgVectorStoreAutoConfiguration` 的 bean 方法签名是：

```java
@Bean
@ConditionalOnMissingBean          // 注意：不带任何属性
public PgVectorStore vectorStore(JdbcTemplate, EmbeddingModel, ...)
```

不带属性的 `@ConditionalOnMissingBean` 按**返回类型**匹配。第一次写这个 bean 时返回类型
写的是 `VectorStore` 接口，结果是自动配置看不见它、照样注册一个同名的 `vectorStore`，
启动直接报：

```
The bean 'vectorStore', defined in PgVectorStoreAutoConfiguration, could not be registered.
A bean with that name has already been defined in AiConfiguration.class
```

**改法是把返回类型写成具体的 `PgVectorStore`**，一处改动，不需要 `exclude`、
也不需要拿属性把它关掉。

顺带一条排查经验：这个自动配置**不在** `spring-ai-pgvector-store` 里，在
`spring-ai-autoconfigure-vector-store-pgvector` 里。`javap` 报「找不到类」时先确认类在哪个 jar。


### 23. 向量库**不能**注册成 `DataSource` bean —— 否则 Druid 退避，全部业务 SQL 打到 PG 上

容器里已经有一个 DataSource（Druid 管的 MySQL 主库），而 Druid 的自动配置带
`@ConditionalOnMissingBean(DataSource.class)`。再往容器里放一个同类型的 bean，它就直接退避 ——
症状是**所有业务 SQL 都发往向量库**，报一堆 MySQL 的表在 PG 里不存在。

所以 `AiConfiguration` 里那个 `DriverManagerDataSource` 是**局部变量**，
只用来给 `PgVectorStore` 包一个 `JdbcTemplate`，不进容器。

也因为这个原因没用 `PgVectorStoreAutoConfiguration`：它取容器里那个 `JdbcTemplate`，
也就是 MySQL 的，建表时会死在 `type "vector" does not exist`。

`DriverManagerDataSource` 不是连接池，每次检索新建一条连接。这里可以接受：
负载是「一次问答一次检索」，为这点流量管一个连接池的生命周期不划算。


### 24. 工具方法一律返回 `String`，不返回实体、不抛异常

`@Tool` 方法的调用方是模型，不是人写的代码：参数是它从用户那句自然语言里猜的，id 可能是它编的。
`OpsTools` 的四个方法因此都守同两条：

**不返回实体** —— 序列化会把 `create_user`、`version` 这些模型用不上的字段一起塞进上下文，
占的是本来就不宽裕的窗口，还容易被它当成业务含义去推理。

**不抛异常** —— 抛出去之后框架会把它转成一段模型看不懂的错误文本，而模型对「工具报错了」
的默认反应是**拿同一个参数再试一次**。返回一句「未找到 id 为 999 的充电桩。
请向用户确认 id，不要自己猜」，它才会改口去问用户。`getPileStatus` 里那三个
`labelOfXxx` 辅助方法包着 try/catch 也是同一个理由 —— 枚举翻不出来时返回
「未知状态(7)」，而不是让 `ParamErrorException` 从工具里冒出去。

时间字段都补一个「距今多久」：模型不擅长做日期减法，而「最后心跳是 3 小时前」
和「是 3 小时前的某个绝对时刻」对它判断离线与否完全是两回事。

这条约束的代价是**断言只能写 `contains`**：这些文案是给模型读的，不是接口契约，
改措辞不该让测试变红。要钉的是「有没有说清是哪一种失败」。见 `OpsToolsTest`。

### 25. 向量库 bean 上的 `@Lazy` **是必须的，不是优化** —— 少了它，「AI 没装」会变成「应用起不来」

`PgVectorStore.builder(...).initializeSchema(true).build()` 在**构造时**就连 PG 建表，
而 Spring 的单例 bean 是在**容器刷新阶段**构造的。这两件事凑在一起的结果是：

> PostgreSQL 没起来 → 容器刷新失败 → **应用起不来，而且是全部测试一起报上下文加载失败**。

这里的要害不是「多了个硬依赖」，而是**失败的性质被换掉了**。
这个功能从第一天起的立场就是「AI 未启用不影响其余接口」（见 `AiConfiguration` 类注释、
`KnowledgeBaseServiceImpl` 用 `ObjectProvider` 注入、`warmUp` 失败只 `log.warn`）——
而 `@Lazy` 缺位时，这个立场在**启动那一刻**就被推翻了：一个和 AI 毫无关系的
`StationServiceImplTest` 会跟着一起红。

**实测**（不是推演）：

| 状态 | `StationServiceImplTest` | 全量 |
|---|---|---|
| 停掉 `chargeops-pgvector` 容器，**不加** `@Lazy` | 5 条全错在 `Error creating bean with name 'vectorStore'` | — |
| 同一状态，**加上** `@Lazy` | 5 / 5 通过 | 400 / 400 |
| 恢复 pgvector | 5 / 5 通过 | 400 / 400 |

**代价要写清楚**：懒加载之后，消费方拿到的是一个**永远不会是 `null` 的代理**，
所以 `requireVectorStore()` 判不出「PG 连不上」——那种情况会以 JDBC 异常的形式
冒到接口上，而不是走「AI 未启用」那段友好提示。这个交换是可以接受的：
**PG 是运维自己要装的依赖，而「Ollama 没装」比「PG 没装」常见得多**，
后者仍然走的是原来的分支。

### 26. 助手回答**不走 markdown 渲染** —— 宁可少好看一点，不引入 `v-html`

模型（qwen3）的输出带一点格式：`### 小标题`、`- 列表`、`**重点**`。按纯文本渲染，
用户会看到满屏的星号和井号；而引一个 markdown 库通常要配 `v-html` ——
那等于把**「模型可以往页面里注入 HTML」**变成一条固定存在的路径。
这段文本的源头是一个会跟着知识库文档和用户提问跑偏的模型，
它不是可信输入，只是「看起来像我们自己写的」。

所以 `web/packages/admin/src/utils/chatText.ts` 只解析**那三种**，
产出一棵由模板渲染的数据树，全程不碰 `v-html`。
模型输出了别的语法（表格、引用块）就原样当文本显示 —— 那只是不好看，不会变成别的东西。

同一类判断在 `AiOpsServiceImpl` 的系统提示词里还有两条，指向的是一件事：
**事实必须来自知识库或工具，不能来自模型的记性** ——
「资料里没有的，直接说知识库里没有这一条，不要凭经验编造故障码的含义或处理步骤」
「需要设备的实时信息时调用工具去查，不要假设」。

共同点是：模型在链路里出现之后，「什么算可信边界」要重新划一遍 ——
它写出来的东西和人写出来的东西，在前端是**长一样的**，但前者不能当可信输入。

| **结束时间填错会把订单锁死在「待结算」，且车主被冻结的钱没有任何接口能释放** | `end` **完全不校验** `endTime` 与 `startTime` 的关系，而 `settle` 要求 `endTime > startTime`（都截断到整秒后比较）。**校验放错了步骤** —— 该在入口拦的没拦，等到了出口才拒。<br>→ `createTime < endTime <= startTime` 这段区间是**缝**：订单在 1 待启动 停多久，缝就有多宽（`startTime` 是运维点「启动充电」的时刻，与建单可以差几分钟）。落进缝里的 `endTime` 会**一路通过**：`end` 返回 `code:1`、订单进 3 待结算，然后 `settle` **永久拒绝**「计费结束时间必须晚于开始时间」。<br>→ 此时**三条退路全断**：`end` 的 CAS 要求 `status = 2`（已是 3）；`cancel` 只收 1；`refund` 只收 5。`ChargingOrderSweepJob` 只管 `4 → 6`，**没有任何任务扫状态 3**。<br>→ 后果：订单永久停在 3，**`frozenAmount` 里的钱永远冻着** —— 既不扣也不退，只能人工改库。<br> **而且那把枪也一起废了**：卡住的订单让 `connector.current_order_id` 永远指着它，于是**这把枪再也建不了单**。管理端**能把枪手工改回 `status = 1 空闲`**（`ConnectorUpdateDTO` 允许 0/1/4/5），于是枪**显示「空闲」但仍然用不了** —— 实测改完再建单被拒：「该充电枪正在使用中，请换一把：已有订单 CO202609210075」。<br>要命的是 `ConnectorUpdateDTO` **没有任何字段能清 `currentOrderId`**，所以**界面无法真正释放这把枪**，只能改库。这一次误操作的代价是：**一笔订单 + 一笔冻结资金 + 一把充电枪**，三者都要人工介入。<br>**已实测复现**：`endTime` 传 `2020-01-01 00:00:00`（比 startTime 早 6 年），`end` 返回 `{"code":1}`，此后 `settle` 永远 `code:0`。<br> 同源的另一半：`endTime` 与 `startTime` **落在同一秒**时同样必死（截断后相等）。实测两分钟内连调 start/end 必然复现 —— 测试和演示时**很容易踩到**。<br>修法（择一）：① `OrderEndDTO.endTime` 加一个「必须晚于本单 startTime」的校验（要在 Service 里查库，Bean Validation 做不到）；② 或者让 `settle` 能接受 `end = start` 并算出 0 段 0 元；③ 或者给状态 3 一个「重报结束读数」的接口。**推荐 ①** —— 校验就该在入口。<br>前端已按 ① 的口径**在提交前挡住**（见 `web/packages/admin/src/views/order/EndOrderDialog.vue` 的 `timeInvalid`），但**那只是让运维踩不到**，后端仍然敞着 | `ChargingOrderServiceImpl.end` / `.settle` / `OrderEndDTO` |
